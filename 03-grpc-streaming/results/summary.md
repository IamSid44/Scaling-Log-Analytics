# Streaming analytics: measured results

Generated by `scripts/plot.py` from `benchmark.csv`. Medians over repetitions. Every row used here produced a final report byte-identical to the sequential C++ reference (113 rows kept, 0 discarded).

Placement: the coordinator, the producer and the query clients run on the first node; each worker runs on its own node. Throughput = records / wall time of the whole client-streaming RPC, measured by the producer, so it includes every backpressure stall. *Cores busy* = a process's CPU time during the stream / the stream's wall time; a Python process that is itself the bottleneck sits near 1.0.

## 0. The model behind every throughput number

In every run where the workers are *not* saturated (30 runs: round-robin, raw wire, no queries, busiest worker < 0.95 cores busy), the time per message on the producer's stream is the producer's own CPU time per message plus a fixed **L = 1.01 ms** (range 1.00-1.02 ms), for messages of 10 to 1,000 records alike:

    time per message = producer CPU per message + L        (in series)
    throughput      = min( W x one worker's rate ,  b / (b x producer CPU per record + L) )

gRPC Python's synchronous client stream sends one message at a time: it pulls the next message from the producer's generator (the producer's CPU work) only after the previous send has completed (L). Predicting each of those runs' throughput from its own producer CPU and the median L: mean error **0.3%**, worst 1.2%.
